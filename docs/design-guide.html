Dash Design Guide

How every Dash screen is built, in dash-electron, dash-core and widgets: which dash-react component to reach for, which theme token colors it, how far apart things sit, and what gets checked before a screen ships.

It describes what the app ships today — the Aurora treatment in src/designSystem.css — and replaces dash-electron/docs/design/DESIGN.md, a 2025 proposal that was never built as written. Every component below is drawn twice, in Aurora dark and light, and most sit next to a real bug it replaces.

Five rules that settle most arguments

dash-react or nothing

Every control, row, bubble and header comes from dash-react. If the piece doesn't exist, add it there first with a story, then use it. No local look-alikes in dash-core or dash-electron.

Tokens, never shades

Color comes from a role (text, muted, surface, hairline, accent) that maps to a theme token. No gray-400, indigo-400, amber-300, and no opacity-50 for muting. That's for screens built in dash-react, dash-core and dash-electron; widget markup may use the Tailwind palette, which follows Dash colors (see Colors in widgets).

One scale

Spacing comes from six steps (4–24px). Radii from three. Text from five sizes. If a value isn't in the scale, the design is wrong, not the scale.

Left-aligned, scannable

Lists, rows and replies read from the left edge. Titles first, status underneath. Centered text is for empty states and nothing else.

Both themes, every time

A screen isn't done until it has been looked at in dark and light. Most of the bugs below were readable in one mode and broken in the other.

Seven roles, mapped to tokens

Screens ask for a role; the role decides the token. Under Aurora the CSS variable wins; elsewhere the ThemeContext key applies. The accent is fixed Aurora violet; a theme's primary color only colors things through the accent role, never a raw bg-primary-* chosen per screen.

Contrast: text up to 17px needs 4.5:1 against what's behind it; 18px and up, or bold, needs 3:1 (WCAG AA, Apple HIG). Check both modes and with Increase Contrast on. Faint text was raised to pass on every surface: #868c9d dark, #626876 light.

Same contrast as Tailwind. Each shade keeps Tailwind's brightness at Aurora's hue, so every pairing keeps its contrast (text-600 on bg-300 stays 5.1:1, text-200 on bg-700 stays 8.3:1). That matters because user themes are stored as palette shades: a theme's light and dark variants pick different shades, and those picks still read correctly.

Same values in both modes. The theme system already switches shades for light mode, so the palette itself doesn't flip — flipping too would undo it. A widget that hard-codes bg-gray-900 stays dark in light mode, as it does today; for light mode, build from dash-react components and theme tokens. Making raw palette classes flip inside widget markup only is a possible follow-up.

Semantic names (bg-surface, text-muted, border-hairline, bg-accent) may come later as clearer, mode-aware options. The widget validator will flag only colors the palette can't reach: hex values in inline styles and arbitrary values like bg-[#123456].

Nothing functional is smaller than 11px (labels, pills, captions); small body text is 12px. For reference, macOS body text is 13pt and its floor is 10pt. Page titles are text-xl; detail titles text-lg; everything else is text-sm or text-xs. Mono is for ids, tool names, package names and keyboard keys — never for prose. Group labels are always SectionLabel; meta lines always Caption2.

--r-sm 9px Buttons, inputs, list rows, tool rows, chips

Hit areas: every clickable thing is at least 28×28px, and never under 20×20px, even when it looks smaller (Apple's macOS default and minimum). Controls sit 12px apart; unframed ones (icons, text links) get 24px of clear space. Borders are 1px hairline. Shadows belong to things that float (modals, menus, popovers), never to rows or bubbles. Sibling groups use gap on a flex or grid parent, not per-item margins.

Every region has an edge; every group has a home

Target · screens are being brought up to it

The rules above size and color single components. These rules size the screen they sit on. The October 2026 screen audit found that most of what looked wrong in the app was layout: regions sharing one surface, groups with no container, text set below its role, and the chat laid out differently in each place. A screen is not done until it passes these in dark and light.

The header ends at a hairline; the list and the detail are each a raised panel; the selected row is filled, not just bolder.

  1. Regions are separated. A screen is header, main and side regions. Neighbouring regions differ by a 1px hairline, a surface step, or both — never neither. In a modal the title bar, toolbar and body are separate; split panes get a divider.
  2. Three surface levels. Page (--bg), region panel, raised group (--raised with a hairline and --r-md). Content groups sit on the raised level. No surface is pure black on a black backdrop; a modal is raised above what it covers.
  3. List and detail. On a page with a list and a detail, the list is its own panel with the search and filters inside its top bar. Every such page uses the same header: title and its one primary on the first row, tabs under it.
  4. Docks share one header and one width. Every dock panel uses PanelHeader and the same width, and its body is one surface with hairlines between header, content and composer.

  1. A titled group lives in a container. Card or Panel, 14px semibold title, hairlines between its rows. SectionLabel labels a list; it never heads a whole section.
  2. Readable text. Anything people read — descriptions, empty states, field values, row titles — is 14px. 12px is only for status and meta lines. Controls (buttons, tabs, segments, filter pills) use 13–14px labels. No italic body text.
  3. Forms. Label (13px) above the field, the field on --raised-2 with an edge, help text (12px) below. A select always shows its value or a placeholder, never blank.
  4. Padding and measure. At least 16px inside panels and 20px in modal bodies. Running text stops at about 70 characters; settings and forms cap at 640px wide.
  5. Icons are Font Awesome. Never emoji, including on cards and quick-start tiles.

Actions, status and selection

Don't — text actions, a bare dot
Slack Pack Pause  Edit  Uninstall

11px text with no frame, a destructive action at rest, and a color with no word.

Do — buttons, a badge, an overflow
Slack Pack Needs Slack

Secondary buttons at 28px, status as a word in a badge, Uninstall inside "…" behind a confirmation.

  1. Actions are buttons. Secondary actions are real buttons at least 28px tall with 13–14px labels. Destructive actions live in the "…" menu and confirm. Each pane uses one action pattern: one primary, secondaries, then "…".
  2. Toolbars hold filters. Every control in a toolbar is the same height (32px). Settings go to Settings or "…"; links go to the page header.
  3. Status is a word. Use StatusBadge (dot plus word). No bare colored dots, no caps text standing in for a tag, and the same word for the same state everywhere.
  4. Selection is visible in both modes. Selected rows, nav items, rail icons, segments and filter chips get an --accent-soft fill (or a filled segment), never only a weight or opacity change. Switch tracks show on and off.
  5. Accent text passes in light mode. Accent-colored text uses the light-mode accent text shade, at least 4.5:1 on light surfaces. Body text is never accent-colored.
  6. One widget header. Every widget uses the same header: title (14px), status line under it, actions on the right. A widget never repeats its title inside its body.

One primary per pane

A pane has at most one Button. Everything else is Button2 or Button3. Destructive actions are danger and only appear in a confirmation, not as a resting button. Icon-only buttons are quiet, 28px square, with a tooltip; a filled square X is never a row action. The primary fill is deep violet so its white label reads at 4.5:1 or better; buttons have no glow. Secondary buttons get a faint tinted fill — never white with black text, which Apple reserves for a toggled-on state. The violet-to-cyan gradient is for brand moments (logo mark, onboarding), never controls.

Before a UI change is called done

Run on screenshots in Aurora dark and light, at the real panel width, with real-looking content — long titles, empty lists, many items.

  • The whole screen was checked, not only the changed component
  • Neighbouring regions differ by a hairline or a surface step
  • Every titled group sits in a Card or Panel
  • Read text is 14px; 12px only for status and meta
  • Secondary actions are buttons; destructive ones sit in “…”
  • Status is a word, not a bare dot
  • Selection is visible in both modes
  • The chat's message box is at the bottom and in view
  • Every control, row and bubble is a dash-react component
  • No palette shades, opacity-muting or arbitrary values (lint:safelist passes)
  • Text readable on its surface in both modes
  • Replies stand off the panel; yours is clearly yours
  • Rows left-aligned; title, then status and age
  • Spacing and radii from the scale, nothing in between
  • At most one primary button in the pane
  • Every label says what clicking does
  • No label repeats the panel it sits in
  • Empty groups hidden; a fully empty view uses EmptyState
  • Truncate only where the full text is reachable (tooltip or detail); nothing overflows the panel
  • Every control works with the keyboard alone; focus is visible
  • Hit areas at least 28×28px (never under 20×20)
  • Readable with Increase Contrast on
  • Motion respects Reduce Motion
  • Nothing functional under 11px
  • npx impeccable detect shows no new findings
  • No hex or arbitrary color values in widgets (palette classes follow the theme)

Reviewed against impeccable and Apple's HIG

From guide to every screen

  1. Approve this guide

    Then it ships as docs/design-guide.html in dash-react, linked from the README and from CLAUDE.md in all three repos.

  2. Fix what the review found in dash-react

    Aurora contrast, button fill, glow and label size (done with this guide); a visible button focus ring and accessible names for icon buttons and inputs (done with this guide); then the light-mode theme pairs (Alert2/3, ProgressBar, Tag, Toast, Table header, opacity-faded text), light-mode status colors, checkbox and radio hit areas, Reduce Motion for pulses, Breadcrumb links, Switch2/3 tracks, and the duplicate InputText export. Each “Known issue” pill comes off as its fix lands.

  3. Tailwind palette follows Aurora

    Shipped in dash-react 1.0.70: every Tailwind color family has a luminance-matched Dash scale (aurora-palette.cjs); dash-electron reads it in its next release. Remaining: screenshot pass of the main screens in both modes before release; teach the widget validator and the AI Widget Builder to flag hex and arbitrary colors; optional semantic names; widget-only light-mode flipping as a later option.

  4. Add the missing pieces to dash-react

    useDashTokens, PanelHeader, ListRow, ChatMessage, ChatToolCall, ChatComposer — each with an AllVariants story in dark and light.

  5. Move the chats onto them

    AI Assistant (ChatCore), Ask the lead (BotChat and AskLead), Create's Planner and Ask, then the Widget Builder — one surface per PR, each with checklist screenshots.

  6. Move the lists and headers

    The dock, Create's start screen, Manage pages and the Dashboard Config modal; replace hard-coded border-indigo-400, bg-amber-400 and text-red-300.

  7. Retire the old doc

    Mark dash-electron/docs/design/DESIGN.md superseded and point it here.
